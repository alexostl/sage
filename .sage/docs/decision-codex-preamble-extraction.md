# ADR — Preamble extraction

## Context

Today, the per-workflow compliance preamble (the "RULES (apply to every
step — non-negotiable)" block injected at the top of every command/skill
file) lives **inline as a bash `case` statement** inside
`runtime/platforms/claude-code/setup/generate-claude-code.sh`, lines
~510–760. The preamble itself is the strongest in-prompt enforcement
channel Sage has on Claude — it is what makes the agent announce
workflow entry, run memory search before work, write spec.md before
code, present `[A]/[R]` checkpoints, and stop using code blocks for
interaction.

Two facts make this brittle:

1. **The plugin generator parses the case statement with awk** (see
   `generate-plugin.sh` lines 136–144, 165, 205–207). This is a
   text-coupled consumer reading text-coupled state from another
   generator. Both files must edit in lockstep, and the awk regex
   relies on quoting conventions that are not part of any contract —
   add a stray quote inside a preamble and the awk silently truncates.

2. **The Codex port is now a third consumer**. Codex generates
   `.agents/skills/<wf>/SKILL.md`. If we keep the preamble inside a
   bash `case`, the Codex generator (`generate-codex.sh`) becomes the
   third tool that has to either re-parse `generate-claude-code.sh` or
   duplicate the strings. Either way, "edit one preamble" becomes
   "edit three places and hope they match." The Claude port's logic
   map (§3.4, §6.2) flagged this exact pain point; the Codex rewrite
   forces resolution because adding a third consumer to a bash-case
   source is the breaking point.

Independently, the Codex port has a **hard char budget** that Claude
never had: research base §4.3 confirms an ~8000-character cap on the
combined skill discovery context across all visible skills. With 16
public skills, every character of preamble text gets multiplied by 16.
The current Claude preamble for `build` is ~1700 chars; multiplied by
16 that's 27 KB — more than 3× over the cap. The preamble cannot ship
into Codex's discovery surface in its current form.

This ADR resolves both problems together: where the preamble lives,
how all three generators read it, and how Codex stays under cap.

## Decision

**One source-of-truth file per workflow, in `core/preambles/<workflow>.md`.**
Each generator (Claude direct, Claude plugin, Codex) reads the file
directly with simple shell tooling — `cat`/`sed`, no awk parsing of
another script.

**Cross-ADR contract with ADR-4 (shared skill manifest):** the teaser
defined here is the **single canonical source** for the Codex SKILL.md
`description:` field. ADR-4 schema does NOT carry a parallel
`short_description` field — that duplication was rejected during user
review. Codex SKILL.md `description:` is generated by reading this
ADR's teaser; ADR-4 only carries platform-shape data
(`public`, `platforms`, `display.codex.allow_implicit_invocation`).
One field, one source, no drift.

The file is **layered**: a short header (the *teaser* — what loads
into Codex's 8000-char discovery surface) and a longer body (the
*full preamble* — what loads when the workflow is actually entered).
Markers in the file separate the two layers so generators can pick
either one without parsing prose.

This decision answers the six open questions from the cycle as
follows:

### Q1 — Where does the preamble live physically?

**`core/preambles/<workflow>.md`** — one file per workflow, named to
match `core/workflows/<workflow>.workflow.md` exactly. So
`core/preambles/build.md` pairs with `core/workflows/build.workflow.md`.

Why not the alternatives:

- **Frontmatter inside `core/workflows/*.workflow.md`** (option B) is
  cleaner conceptually (one file per workflow, full stop) but pushes
  multi-line YAML strings (`preamble: |\n ...`) into a file that
  shells, awk, sed, and Python all parse. YAML inside YAML
  frontmatter is fragile. Bash generators would need a YAML parser.
  Rejected for tooling cost.
- **Inline markers in workflow body** (option C — `<!-- PREAMBLE
  START --> ... <!-- PREAMBLE END -->`) keeps the preamble adjacent
  to the workflow it constrains, but it bakes a "preamble" concept
  into the workflow document, which is supposed to be platform-
  neutral. The preamble is platform glue, not workflow content.
  Rejected for boundary leakage.

### Q2 — One preamble or per-platform variants?

**One source preamble per workflow, with two layers, plus a small
per-platform translation step done by the generator.** Not a separate
file per platform.

The full preamble text — "Read persona X", "MEMORY FIRST", "spec.md
MUST EXIST", "[A] = REVIEW = run sub-agent", "Save artifacts to
.sage/", "Never use code blocks for interaction" — is the same
behavior contract across platforms because Sage's behavior is the
same across platforms (V2 outcome parity).

What differs is *where* the text lands and *how much* of it lands:

- **Claude direct deploy** → full body to top of
  `.claude/commands/<wf>.md`. No char budget.
- **Claude plugin** → full body to top of
  `tools/sage-claude-plugin/skills/<wf>/SKILL.md`. No char budget.
- **Codex** → **teaser only** (≤300 chars) to skill `description:`
  field in `.agents/skills/<wf>/SKILL.md`. Full body lives in the
  same file, **below** the YAML frontmatter, so it loads only when
  the skill is mentioned (`$build`) and not at discovery time.

Per-platform variants are achieved by the generator picking layer
(teaser vs full) — not by maintaining separate per-platform preamble
files. Three files would re-create the drift problem we are removing.

### Q3 — Codex 8000-char cap

The cap is **discovery-context** specifically: the SKILL.md
`description:` block of every visible skill is summed up at session
start. Skill body content below the frontmatter loads only when the
skill is mentioned by name (lazy load). This is consistent with the
research base §4.3 framing.

Therefore the rule is: **only the teaser goes into `description:`.**
Full body goes into the SKILL.md body section, below `---`.

Char budget math (16 visible public skills):

| Item | Chars per skill | × 16 skills |
|------|------|------|
| Teaser (target) | 250 | 4000 |
| Skill name + name field | ~30 | 480 |
| `description: >-` wrapper | ~20 | 320 |
| **Subtotal in discovery** | **~300** | **~4800** |
| Headroom under 8000 | | **~3200** |
| Full body (lazy-loaded, NOT in discovery) | 1500–2000 | n/a |

Headroom is comfortable. If a teaser overshoots 300 chars, `sage
doctor` flags it (see "Failure modes" below).

### Q4 — Boundary with AGENTS.md

`AGENTS.md` is loaded **once per session**, has its own 32 KiB cap
(research base §4.2), and is shared by every skill in that session.
Per-skill preamble is loaded **on skill mention**.

The line is:

| Concern | Lives in | Why |
|---------|----------|-----|
| "Save artifacts to .sage/" | AGENTS.md | Cross-skill, never not-true |
| "Never use code blocks for interaction" | AGENTS.md | Cross-skill |
| "MEMORY FIRST before Standard+ work" | AGENTS.md | Cross-skill rule |
| "[A]/[R] checkpoint vocabulary" | AGENTS.md | Cross-skill protocol |
| "spec.md MUST EXIST before build" | `core/preambles/build.md` | Build-specific gate |
| "Complete 3 elicitation rounds before design" | `core/preambles/architect.md` | Architect-specific gate |
| "Root cause before any fix" | `core/preambles/fix.md` | Fix-specific gate |
| "Read persona <name>" | per-workflow preamble | Each workflow has its own persona |

**Test:** if removing the rule from one workflow's preamble would
make the same rule appear in 3+ other preambles, it belongs in
AGENTS.md. Otherwise, per-workflow.

This is also why the preamble file does not need to repeat
cross-skill rules. A junior-dev mistake would be to paste everything
everywhere "for safety" — that bloats the discovery surface and makes
maintenance a nightmare. Trust AGENTS.md to carry the constants.

### Q5 — Generator integration (all three generators)

All three read `core/preambles/<workflow>.md` directly. No generator
reads another generator. The format of the file is rigid enough that
**bash + sed + cat is sufficient**; no Python helper is required at
this layer.

File format (concrete schema in next section):

```
---
teaser: |
  short discovery text (≤300 chars)
---

# Full preamble body

Long body text, multi-line, markdown allowed.
```

How each generator reads it:

- **`generate-claude-code.sh`** (Claude direct): reads
  `core/preambles/<wf>.md`, strips the frontmatter, prepends the
  body to `.claude/commands/<wf>.md`. Replaces the current `case`
  statement entirely. Two lines of sed instead of 250 lines of bash.
- **`generate-plugin.sh`** (Claude plugin): same — reads the same
  file, strips frontmatter, prepends body to
  `tools/sage-claude-plugin/skills/<wf>/SKILL.md`. The awk block
  parsing the other generator is **deleted**. This is the main win.
- **`generate-codex.sh`** (Codex, new): reads the same file, takes
  *only the `teaser:` field* for `description:` in SKILL.md
  frontmatter, then writes the body below the frontmatter. Bash
  + sed; teaser extraction is one `sed -n` call.

If a workflow has **no preamble file**, generators emit a warning
and skip the preamble injection for that workflow. This is the
fallback that keeps the build green during migration.

## Schema / format

Concrete example: `core/preambles/build.md`

```markdown
---
teaser: |
  Sage build workflow. RULES: persona=developer, memory search before
  work, spec.md MUST EXIST before code, [A] runs review sub-agent,
  paste real test output, never code blocks for interaction.
---

# Build workflow preamble

RULES (apply to every step — non-negotiable):

- PERSONA: Read sage/core/agents/developer.persona.md for your mindset.
- Announce: "Sage → build workflow." before starting work
- MEMORY FIRST: Before writing spec, plan, or starting implementation,
  search sage-memory with the feature domain as query (limit: 5), then
  search again with filter_tags: ["self-learning"] (limit: 5). Use
  findings to avoid past mistakes. This is MANDATORY, not optional.
- Standard+ scope: spec.md MUST EXIST at .sage/work/ before
  implementing. "Design is clear" is NOT a spec. "We discussed this"
  is NOT a spec. A spec is a FILE. No file = no implementation.
- [A] = REVIEW: When user picks [A] at spec or plan checkpoint,
  you MUST run auto-review sub-agent BEFORE proceeding to the next
  phase. [S] = Skip review (approve without review). Present [A]
  Review / [S] Skip review at every spec and plan checkpoint.
- GATE 3 INDEPENDENT: Code quality review (Gate 3) MUST use
  sub-agent when Task tool is available.
- CODING PRINCIPLES: Load
  sage/core/capabilities/execution/coding-principles/SKILL.md before
  every implementation task.
- Save ALL artifacts to .sage/work/ or .sage/docs/ — never inline-only
- Verify: PASTE actual test output before claiming done — no summaries
- If user corrects your approach, store as self-learning before continuing
```

Why this schema (junior-dev framing):

- **Frontmatter is YAML.** Every Sage tool already reads YAML
  frontmatter on artifacts. Reusing the convention instead of
  inventing a new marker keeps cognitive load low.
- **`teaser:` uses block-scalar `|`** so multi-line teasers are
  legal. Most teasers will be 1–3 sentences and fit on one line, but
  block-scalar avoids the "oh, must be single-line" gotcha.
- **Body below `---` is plain markdown.** No special directives. The
  generator just `sed`s out the frontmatter and prepends the rest.
  If the file has no frontmatter (legacy/early migration), the
  generator treats the whole file as the body and emits a warning
  that there is no Codex teaser.

Reading the body in bash:

```bash
# Strip YAML frontmatter from preamble file
preamble_body=$(sed '/^---$/,/^---$/d' "$CORE/preambles/$wf_name.md")
```

Reading the teaser:

```bash
# Extract teaser block-scalar (between teaser: | and next ---)
teaser=$(sed -n '/^teaser: |/,/^---$/{/^teaser: |/d; /^---$/d; s/^  //; p;}' \
  "$CORE/preambles/$wf_name.md")
```

Both are 1-line shell snippets. Junior-dev readable.

## Generator integration

### Claude direct (`generate-claude-code.sh`)

**Before** (current, lines ~510–760): bash `case` statement with
~250 lines of inline preamble text per workflow.

**After**: replace the case with a loop call to a small helper:

```bash
for wf in "$CORE"/workflows/*.workflow.md; do
  basename_wf=$(basename "$wf" .workflow.md)
  PREAMBLE_FILE="$CORE/preambles/$basename_wf.md"

  if [ -f "$PREAMBLE_FILE" ]; then
    PREAMBLE=$(sed '/^---$/,/^---$/d' "$PREAMBLE_FILE")
  else
    PREAMBLE=""
    echo "WARN: no preamble for $basename_wf" >&2
  fi

  # ... existing prepend logic uses $PREAMBLE unchanged
done
```

Behavior change: zero, when all preamble files exist. Test parity
verified by diffing generator output against pre-extraction baseline
(see Migration plan).

### Claude plugin (`generate-plugin.sh`)

**Before**: awk block parsing the other generator's `case` statement
(lines 136–144 + 165 + 205–207).

**After**: replace awk block with the same `sed` call as direct
generator. Delete the `PREAMBLE_CACHE` mktemp dance. The two
generators now read the same source file independently, which is
the whole point of extraction.

### Codex (`generate-codex.sh`, new file in this rewrite)

For each public workflow, emit `.agents/skills/<wf>/SKILL.md`:

```bash
TEASER=$(sed -n '/^teaser: |/,/^---$/{/^teaser: |/d; /^---$/d; s/^  //; p;}' \
  "$CORE/preambles/$wf_name.md")
BODY=$(sed '/^---$/,/^---$/d' "$CORE/preambles/$wf_name.md")

cat > ".agents/skills/$wf_name/SKILL.md" <<SKILLEOF
---
name: $wf_name
description: >-
  $TEASER
---

$BODY

$WORKFLOW_BODY_FROM_CORE_WORKFLOWS
SKILLEOF
```

The Codex skill discovery sees `description:` (≤300 chars). When
the agent mentions `$build`, Codex loads the body — full preamble
plus workflow content — into context.

## Boundary with AGENTS.md

Project `AGENTS.md` (loaded once, 32 KiB cap, shared across skills)
carries:

- "Save artifacts to .sage/work or .sage/docs" — universal
- "Use [1] [2] [3] for choices" — universal protocol vocabulary
- "Use [A] Approve / [R] Revise at checkpoints" — universal
- "Never code blocks for interaction" — universal output rule
- "Search sage-memory before Standard+ work" — universal rule
- Worktree scope rule (from ADR-1 W1)
- UPS-token vocabulary listing (from ADR-2 W2)

Per-workflow preamble carries:

- "Read persona X" (specific persona file path per workflow)
- Workflow-specific gate text (spec MUST EXIST / brief MUST EXIST /
  root cause before fix / 3 elicitation rounds / etc.)
- Workflow-specific tool requirements (Lightpanda for QA, Task
  tool for review)
- Workflow-specific scope language (one change per iteration in
  autoresearch; never main branch in autoresearch)

`AGENTS.override.md` at user level (research base §6.2.6, do #6)
carries selfhosttainer overrides — not part of v1 framework
output, but the boundary is clear: it is a user-machine layer above
the project layer, never written by the framework generator.

## Char budget for Codex

Detailed accounting (16 public skills):

```
Discovery surface (sum of all SKILL.md frontmatter at session start):

per skill:
  name field            ~30 chars   ("name: design-review\n")
  description wrapper   ~20 chars   ("description: >-\n  ")
  teaser content       ≤250 chars
  closing ---           ~5 chars
  blank lines           ~5 chars
  total per skill      ≤310 chars

× 16 skills            ≤4960 chars
discovery cap            8000 chars
headroom                ≥3040 chars  (38%)
```

Headroom is enough for: skill name growth, future 17th skill, AGENTS.md
file-list metadata that may also count toward discovery context (the
exact rule is documented in research base §4.3 but not byte-precise;
38% headroom absorbs ambiguity).

If teaser drift pushes a single skill over 300 chars, `sage doctor`
detects it (see Failure modes). The cap is enforced per-skill at
generation time, not just at session time, to give a short feedback
loop.

Lazy-loaded body (per skill, NOT counted in discovery):

```
per skill:
  full preamble body   1200–2000 chars
  workflow body        1000–4000 chars
  total per skill      2200–6000 chars
```

These load only when the skill is mentioned. They do not need to fit
in 8000 chars combined; they are loaded one at a time.

## Options considered

### Option A (chosen) — `core/preambles/<wf>.md` with teaser/body layers

Plus:
- One file per workflow, paired by name with `core/workflows/<wf>.workflow.md`.
- Plain YAML frontmatter + markdown body — every existing Sage parser
  already handles this shape.
- All three generators read the same file independently with `sed` —
  no generator-to-generator coupling.
- Two layers (teaser ≤300 chars, full body) handle the Codex 8000-char
  cap without forcing Claude to truncate anything.
- Junior-dev legible: no Python helper, no DSL, no special markers.

Minus:
- Adds 16 new files in `core/`. Repo grows. Mitigated by them being
  tiny (~1.5 KB each), discoverable (`ls core/preambles/`), and named
  identically to the workflows they pair with.
- Two-layer schema (teaser + body) is a small concept to learn —
  authors must write the teaser explicitly, and not just wave a hand
  at "Codex will figure it out."

### Option B — Frontmatter field `preamble:` inside `core/workflows/<wf>.workflow.md`

Plus:
- One file per workflow, period. No new directory.
- Maximum locality: rule and its motivation live next to each other.

Minus:
- Multi-line YAML block-scalar inside a markdown file's frontmatter
  is fragile in bash parsers. Junior-dev mistake: indenting the
  body inconsistently silently truncates the parsed value.
- `core/workflows/*.workflow.md` is declared "modify-with-care" in
  manifest C4 because it has cross-platform impact. Adding a Codex-
  motivated `preamble:` field is exactly the kind of change C4
  warns about — bleeds Codex concerns into a shared file.
- Bash sed for "extract a multi-line YAML scalar" is non-trivial.
  We would end up needing Python (`yq` or a tiny parser), which
  pushes us into ADR-4 territory before ADR-4 has been decided.

### Option C — Inline markers in workflow body

`<!-- PREAMBLE START --> ... <!-- PREAMBLE END -->` inside the
workflow markdown body, generators extract between markers.

Plus:
- Locality without YAML fragility.
- Bash `sed -n '/PREAMBLE START/,/PREAMBLE END/p'` is simple.

Minus:
- Markers are noise inside the workflow document. The workflow is
  meant to be a human-readable description of how the workflow runs;
  burying compliance text inside it dilutes that.
- Same C4 concern as option B: workflow files are platform-neutral
  contracts; adding generator-only markers blurs the boundary.
- No clean way to express the teaser/body split without two marker
  pairs, which compounds the noise.

### Option D — Status quo (bash case)

Plus: no migration, no new files.

Minus: every problem listed in Context. The Codex generator would
become the third consumer of an awk-coupled script. Rejected.

## Trade-offs

The big trade-offs that are worth user review:

1. **Centralisation vs locality.** Option A puts all preambles in one
   directory (`core/preambles/`); the workflow file is somewhere
   else. The cost is one more directory to navigate; the benefit is
   that "edit a preamble" is one action against one file with no
   special tooling. Junior-dev framing: tradeoff favors "easy to
   change" over "easy to find next to its workflow."

2. **Bash-parsable format vs YAML richness.** Option A uses YAML
   frontmatter only because every Sage tool already parses it. We
   are not pushing structured data through YAML — only text blocks.
   If we wanted typed preamble metadata (e.g., `requires:
   [task_tool, lightpanda]`), this format would not carry it
   cleanly. We accept this; metadata of that kind belongs in the
   shared skill manifest (ADR-4 territory), not in a preamble.

3. **Char budget vs informativeness.** The 300-char teaser
   constraint is real and enforced. Authors will sometimes find
   themselves cutting useful text. Mitigation: the body still loads
   lazily, so anything cut from the teaser is not *removed*, just
   *deferred* until skill mention. This is the right shape for
   Codex's discovery model — discovery says "this skill exists and
   roughly does X"; activation loads the rules.

## Failure modes

**FM-1 — Preamble file missing for a workflow.**
- Detection: generator prints WARN to stderr and skips preamble
  injection for that workflow.
- Impact: the generated command/skill has no rules header. Agent
  may skip MEMORY FIRST, write code without spec, etc.
- Mitigation: `sage doctor` checks that for every
  `core/workflows/<wf>.workflow.md` there is a corresponding
  `core/preambles/<wf>.md`. Missing pair = doctor warning.

**FM-2 — Teaser exceeds 300 chars.**
- Detection: generator measures `wc -c` of extracted teaser; if >300,
  generator fails with an error. Better to fail at generation than
  silently truncate at discovery time.
- Impact (if we let it slip): Codex truncates the discovery context
  unpredictably. A late-listed skill might disappear from discovery
  entirely.
- Mitigation: per-file char count check at generation; `sage doctor`
  also computes total discovery char usage and warns if over 6000
  (75% of cap) to give margin.

**FM-3 — Cross-platform drift in preamble content.**
- Detection: only one source file per workflow exists, so drift
  within a workflow is structurally impossible. Drift between
  workflows (e.g. build and fix preambles disagree on `[A]`
  semantics) is detectable by reviewing all 16 files together — a
  task `sage doctor` does not currently do, but could.
- Mitigation: documented in `core/preambles/README.md` (small
  authoring guide); review during ADR-4 / ADR-5 to land canonical
  vocabulary.

**FM-4 — Frontmatter malformed (broken `teaser:` block).**
- Detection: generator's `sed -n '/^teaser: |/,/^---$/'` extraction
  returns empty. Generator treats this as missing teaser → fails
  loudly (not silently).
- Mitigation: `sage doctor` parses each preamble file with the same
  sed snippets the generator uses, and reports any file that yields
  an empty teaser.

**FM-5 — Codex discovery context overflow at session start.**
- Detection: `sage doctor` totals all 16 teasers + frontmatter
  wrappers and warns if the result is over 6000 chars (75% of cap)
  or fails over 8000 chars.
- Mitigation: hard fail at generation if the project has overflow;
  fix is to shorten the teaser of whichever skill grew.

## Migration plan

This is mechanical. Tests are the safety net.

### Step 1 — Extract preambles

For each of the ~14 workflows with a current `case` arm in
`generate-claude-code.sh`:

1. Copy the inline preamble string into a new file
   `core/preambles/<wf>.md`.
2. Author a teaser (≤300 chars) summarising the rules.
3. Wrap as YAML frontmatter (teaser) + markdown body.
4. Verify: `sed '/^---$/,/^---$/d' core/preambles/<wf>.md` produces
   the same body that was inside the bash case.

### Step 2 — Update Claude direct generator

1. Replace the `case` statement (lines ~510–760) with the loop
   reading from `core/preambles/`.
2. Run generator against `sage-selfhost` repo (dogfood) and a test
   project. Diff generated `.claude/commands/*.md` files against the
   pre-change baseline. **Expect zero functional diff** (whitespace
   normalisation aside).

### Step 3 — Update Claude plugin generator

1. Delete the awk preamble cache block (lines 136–144).
2. Delete the `grep "^${wf_name}|||"` lookup (line 165).
3. Replace with same `sed` call against `core/preambles/<wf>.md`.
4. Run generator against `tools/sage-claude-plugin/`. Diff
   generated SKILL.md files against pre-change baseline. **Expect
   zero functional diff.**

### Step 4 — Build Codex generator (new file)

1. `generate-codex.sh` reads `core/preambles/<wf>.md` and emits
   `.agents/skills/<wf>/SKILL.md` per the schema in this ADR.
2. Char budget validation step at end of generator:
   `sum_of_teasers <= 6000 chars` (75% of cap) — warn, fail at 8000.

### Step 5 — Doctor checks

Add to `sage doctor`:
- For every `core/workflows/<wf>.workflow.md`, assert
  `core/preambles/<wf>.md` exists.
- For every preamble file, assert teaser parses non-empty.
- For every preamble file, assert teaser ≤300 chars.
- Sum all teasers (+ wrappers) and warn if >6000.

### Step 6 — Verification

The acceptance test for the migration is **byte-equivalent generator
output on Claude side**:

```bash
# Pre-extraction
git stash; bash bin/sage update; cp -r .claude /tmp/baseline-direct
cp -r tools/sage-claude-plugin /tmp/baseline-plugin
git stash pop

# Post-extraction
bash bin/sage update
diff -r /tmp/baseline-direct .claude
diff -r /tmp/baseline-plugin tools/sage-claude-plugin
```

Both diffs must be empty (or whitespace-only) before the migration
is considered complete. If diffs show real content changes, the
extraction altered semantics — go back and find the missed text.

For Codex side, the acceptance test is the outcome harness from
brief.md C5 — `codex exec --json` 12–15-prompt pilot, including
prompts that test workflow entry, MEMORY FIRST behavior, and gate
respect. If extraction broke the rules, harness prompts fail.

## Consequences

**Confirmed contract with ADR-4 (shared skill manifest).** ADR-4
landed on per-skill `manifest:` blocks in existing workflow/SKILL
frontmatter, compiled to `core/_compile/skills.compiled.json`. ADR-4
deliberately does NOT carry preamble text or any duplicate of the
teaser — preamble content lives only here. The Codex generator
pipeline is:

1. Read `skills.compiled.json` (ADR-4) to learn which skills are
   public on Codex.
2. For each public-on-codex skill, read `core/preambles/<name>.md`
   (this ADR) to extract teaser + body.
3. Emit `.agents/skills/<name>/SKILL.md` with `description:` = teaser
   and body below frontmatter = preamble body + workflow content.
4. Emit `agents/openai.yaml` only when ADR-4 manifest signals
   `display.codex.allow_implicit_invocation: false` (internal skills).

The dependency is one-way: ADR-4 lists workflow names + platform
flags; this ADR provides the text content each name binds to.

**Required of `sage doctor`.** New checks listed in FM-1, FM-2,
FM-4, FM-5. Each check is a few lines of bash; the doctor surface
already exists per the brief (Nice To Have section).

**Required of regression tests.** The migration's "byte-equivalent
generator output" test (Step 6) becomes a permanent regression
test — any future preamble change is checked by re-running both
generators and confirming the diff is intentional.

**Out of scope for this ADR.**
- AGENTS.md content — covered by ADR-5 (instruction surfaces).
- Public-vs-internal skill list — covered by ADR-4 (shared manifest).
- The exact text of each preamble post-migration — that is content
  work, not architecture work. Migration Step 1 carries forward the
  current text; refinement happens in build phase.

## Open questions for review

1. **Teaser char limit.** 300 chars is conservative — actual
   per-skill discovery cost may be lower (research base §4.3 gives
   the sum cap, not a per-skill cap). If user wants more headroom
   for AGENTS.md or future skills, drop to 200. If user is willing
   to spend the budget for richer teasers, raise to 400. Default:
   300.

2. **Preamble file location naming.** `core/preambles/` is the
   proposed name. Alternatives: `core/workflows/preambles/` (nested
   under workflows, signals pairing) or `core/skills/<name>/preamble.md`
   (co-located with eventual ADR-4 skill manifest). The latter is
   only viable under ADR-4 variant 4a (decentralized). Default:
   flat `core/preambles/` for v1.

3. **Migration timing.** This ADR can land before ADR-4 is decided
   because it is manifest-shape-agnostic. But the actual file
   rename / restructure work is cheaper to do once we know ADR-4's
   answer (so we don't move files twice). Recommend: approve this
   ADR now (architectural decision frozen), implement migration
   after ADR-4 is approved (file moves done once).
