## Adapter File Inventory

The Codex adapter lives in `runtime/platforms/codex/` with the following structure:

```
runtime/platforms/codex/
├── README.md                    # Primary status & design doc (12 KiB)
├── INSTALL.md                   # Installation instructions for users
├── HOOKS.md                      # Opt-in hook starter pack documentation
├── AUTOMATIONS.md               # Native Codex automation templates (no generation)
├── platform.yaml                # Platform capability matrix & path declarations
├── hooks.example.json           # Hook configuration template for copy-paste adoption
├── setup/
│   └── generate-codex.sh        # Main generator (1003 lines) — wires all outputs
├── hooks/
│   ├── session-start.sh         # [Opt-in] Rich session context from .sage/work/*
│   ├── pre-prompt.sh            # [Opt-in] UserPromptSubmit gate (344 lines)
│   ├── pre-bash.sh              # [Opt-in] Narrow bash destructive-command guard
│   ├── post-bash.sh             # [Opt-in] Review reminder after mutations
│   ├── lib/
│   │   ├── active_state.py      # Sticky-state computation (295 lines)
│   │   └── verification_check.py # Rule verification for artifact validation (209 lines)
│   └── tests/                   # Full hook test suite (bash + pytest)
└── tests/
    └── run-regression.sh        # E2E regression suite (239 lines)
```

**Key roles:**
- **platform.yaml** — declares Codex as Tier 1, lists capabilities (subagents, worktrees, skill-auto-activation), command-prefix handling, path mappings to project files
- **generate-codex.sh** — orchestrates all generated outputs; reads `.sage/config.yaml` for prefix + direct-skill deploy flags; emits AGENTS.md, .agents/skills/, and refreshes .codex/config.toml
- **hooks/** — optional enforcement scaffold; no hooks are generated by default; teams copy example.json + scripts if they want opt-in gates
- **HOOKS.md** — architectural guide to why pre-prompt.sh matters (UserPromptSubmit is the only pre-turn Codex gate available), how to tune regex patterns, why status-aware matching beats global

## Generated Surfaces (What `sage init --platform codex` Produces)

### **AGENTS.md** (Generated by generate-codex.sh:145-461)

- **Generator path:** `runtime/platforms/codex/setup/generate-codex.sh` → outputs directly to `$SAGE_ROOT/AGENTS.md`
- **Template source:** Heredoc at line 145 (static, 314 lines)
- **What it asserts about behavior:**
  - 8 mandatory Process Constitution rules + 3 workflow gates (Build, Fix, Architect)
  - Observable compliance signals per rule (e.g., "first line says `Sage → [workflow]`", both spec.md and plan.md on disk)
  - Codex-native interaction zones (Choice/Approval/Next Step/Open)
  - Subagent delegation preference for review (Codex multi-agent execution)
  - Explicit note: hooks are opt-in, constitution applies always
  - Codex-native surfaces: `/review` for diff, `$sage`/`$build`/`$fix` for workflow entry
  - MCP config lives in `.codex/config.toml` managed block; user-owned config survives regeneration
- **Prefix handling:** After generation, `codex_prefix_text()` (line 36) rewrites all `$build` → `$sage:build` if `command_prefix: true` in `.sage/config.yaml`
- **Size:** ~12 KiB, well below Codex 32 KiB session doc cap

### **.agents/skills/** (Generated by generate-codex.sh:765-990)

- **Workflow skills** (14 files, one per `.workflow.md` in core/workflows/):
  - Path pattern: `.agents/skills/<workflow>/SKILL.md` or `.agents/skills/sage:<workflow>/SKILL.md` (if prefix=true)
  - Each generated with:
    - Frontmatter: `name:`, `description:` from platform.yaml lookup
    - First-turn **PREAMBLE** block: "RULES (apply to every step — non-negotiable)" (lines 533-762)
      - Reiterates AGENTS.md enforcement scoped to that workflow
      - Examples: build PREAMBLE (line 539) enforces memory search + FILE CHECKS gate; fix PREAMBLE (line 561) enforces ROOT CAUSE FIRST
    - Workflow body: stripped from `core/workflows/<name>.workflow.md` (line 928)
  - Special cases:
    - **sage** (line 783): self-contained router (no source file, renders inline with step-by-step state reading)
    - **review** (line 850): delegates to fresh subagent when available, falls back with disclosure if not
  - Prefix handling: if prefix=true, skill renamed and frontmatter `name:` field updated
  - Stale-variant cleanup: `remove_stale_skill_variant()` (line 120) prunes alternate naming (e.g., if toggling from `build` to `sage:build`, removes old `build/` dir)

- **Direct skills** (optional, deploy_direct_skills: true in .sage/config.yaml):
  - Copied from `sage/skills/*/` (line 944); workflow wins namespace (line 963)
  - Includes supporting dirs: references/, templates/, examples/, patterns/, anti-patterns/, integration/, scripts/, resources/, constitution/, gates/

- **Naming conventions:**
  - Default (no prefix): `build`, `fix`, `architect`, `review`, `status`, etc.
  - Prefixed (command_prefix: true): `sage:build`, `sage:fix`, etc. (sage-navigator and /review exempt)
  - Both variants cleaned up to prevent collisions on prefix toggle

### **.codex/config.toml** (Generated by generate-codex.sh:993-995)

- **Generator path:** Calls `runtime/mcp/json_to_toml.py` (line 994)
- **Strategy:** Marked-block preservation
  - If config already exists, `json_to_toml.py` searches for `# >>> SAGE MANAGED BLOCK START` / `# <<< SAGE MANAGED BLOCK END` (defined in json_to_toml.py:25–26)
  - Translates `.claude/mcp.json` or `.sage/mcp.json` (legacy) → TOML `[[mcp_servers]]` entries inside managed block
  - Preserves all user-owned config outside the block (e.g., `model = "gpt-5.4"`, `[features]`, `[mcp_servers.native_keep]`)
  - On `sage update`, only the managed block is refreshed
- **MCP encoding:**
  - TOML table format: `[[mcp_servers.<name>]]` with `command`, `args` keys
  - Handles bare keys vs quoted keys for special characters
  - Example (from json_to_toml.py:54–58): complex nested dicts rendered as inline TOML `{ key = value, ... }`
- **Codex-native feature toggles** (documented in json_to_toml.py:95–100):
  - `[features] codex_hooks = true` (commented example)
  - `project_doc_fallback_filenames` (example shown)
  - `project_doc_max_bytes` (defaults to Codex limit)
- **No generation of hooks.json by default** — hooks are entirely opt-in; teams manually copy `hooks.example.json` to `.codex/hooks.json` when desired

### **Hooks** (Opt-In, No Default Generation)

- **What's wired by default:** Nothing. Hooks are experimental in Codex; all four scripts are examples only
- **What's opt-in:**
  1. Enable in `.codex/config.toml`: `[features] codex_hooks = true`
  2. Copy `hooks.example.json` → `.codex/hooks.json`
  3. Copy hook scripts from `runtime/platforms/codex/hooks/*.sh` → `.codex/hooks/`
- **Where activation lives:** `.codex/hooks.json` (Codex-native hooks config) + `[features].codex_hooks` toggle in `.codex/config.toml`
- **Hook events wired** (from hooks.example.json):
  - `SessionStart` (line 3–12): runs `session-start.sh` on startup/resume/clear/compact
  - `UserPromptSubmit` (line 14–22): runs `pre-prompt.sh` **pre-turn gate**
  - `PreToolUse` matcher=Bash (line 24–33): runs `pre-bash.sh`
  - `PostToolUse` matcher=Bash (line 35–44): runs `post-bash.sh`

### **Automations**

- **What's generated:** Nothing
- **Why:** Codex automations are a native platform feature, not a Sage-managed scheduler. No generation needed.
- **What's documented:** `AUTOMATIONS.md` contains copy-paste templates for four common patterns:
  - Repo Brief (weekly standalone)
  - CI Triage (standalone)
  - Review Follow-Up (thread)
  - Reflect/Retro (thread)
- Users adapt the prompts and wire them directly in Codex settings

### **.sage/** (Shared Project State)

- **Generated once (if missing):** `.sage/decisions.md` (header + init entry), `.sage/docs/`, `.sage/work/`, `.sage/gates/`
- **Deployed:** Gate scripts from `core/gates/scripts/*.sh` → `.sage/gates/scripts/`
- **Gate config:** `core/gates/_config/gate-modes.yaml` → `.sage/gates/gate-modes.yaml`
- **Preserved on regeneration:** All existing content in `.sage/` across all adapters (shared contract)

## Workflow ↔ Adapter Coupling

### In `core/` — Where Workflows Reference Codex Specifics

The coupling is **minimal and intentional**:

- **core/capabilities/execution/implement/SKILL.md** (only explicit mention):
  - Line: "On Tier 1 platforms (Claude Code, Codex), each task implementation MAY be…"
  - No concrete Codex-specific enforcement, just acknowledgment that Tier 1 platforms support subagents

- **No command-prefix handling in core/** — all command rewrites happen in the generator:
  - `generate-codex.sh:codex_prefix_text()` (line 36–86) uses Python regex to inject prefixes into AGENTS.md + SKILL.md after generation
  - Rewrites `[$]<cmd>` → `[$]sage:<cmd>` and `.agents/skills/<cmd>` → `.agents/skills/sage:<cmd>` (lines 73–82)
  - Does NOT touch `/review` (native Codex command)

- **No hook event names in core/** — hooks are purely platform-local:
  - `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse` are Codex JSON hook event names
  - Referenced only in `runtime/platforms/codex/hooks.example.json` and `HOOKS.md`

- **No AGENTS.md PREAMBLE injection points in core/** — workflow skill PREAMBLE is generated per-platform:
  - `generate-codex.sh:workflow_preamble()` (line 533) outputs the Codex-native RULES block
  - Claude Code generates its own equivalent in the plugin generator

- **skill-load assumptions:** No platform-specific assumptions
  - `generate-codex.sh` treats `.agents/skills/` as the discovery surface (line 222 in README notes this is Codex's current behavior)
  - `.codex/skills/` is documented as an optional native Codex layer Sage does not dual-support (README line 76–79)

- **No skill-stub vs full logic:** Direct skills copy all supporting subdirs (line 983–985); no platform-specific deployment mode

### Decision Registry Coupling

- `.sage/decisions.md` is shared across all adapters; no Codex-specific schema
- Gate compliance signals in AGENTS.md (Rule 0–8) are platform-agnostic prose; Codex just emphasizes them more strongly via the pre-prompt.sh gate

### Claude Code Capabilities That Codex Lacks (Conservative Port)

| Feature | Claude Code | Codex | Codex Status |
|---------|-------------|-------|--------------|
| **Slash commands** | `/sage`, `/build`, `/fix`, etc. (16+ custom Sage commands) | `$sage`, `$build` (skill-driven, not custom slash) | Native Codex discovery; no custom slash layer |
| **settings.json** | Full hook + permission orchestration | `.codex/config.toml` marked block | TOML, not JSON; Sage manages only one block |
| **Plugin model** | `.claude-plugin/` with marketplace.json | None (skills only via `.agents/skills/`) | Codex doesn't have plugin marketplace; uses workspace skills |
| **Lifecycle hooks** | `SessionStart`, `SessionEnd`, `PrePrompt`, `PreToolUse`, `PostToolUse`, `PostPrompt` (6 hook events) | `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse` (4 events) | `UserPromptSubmit` is Codex's unique pre-turn gate (strongest lever) |
| **Guardian approval** | `features.guardian_approval` + subagent routing | Documented as optional follow-up (README line 286) | Not implemented; would need Codex `[agents.<name>]` subagent + guardian flag |
| **Skill activation** | Carried across turns in a session (sticky) | Eager-loaded by name only; bodies read on activation, not carried (line 565 in HOOKS.md) | One-shot PREAMBLE per skill invocation; constitution in AGENTS.md once per session |
| **File-edit PreToolUse gating** | Available | Only Bash gate available (README line 258) | **CONTRADICTED by Stream D — apply_patch matcher exists** |
| **Windows support** | Yes | No (README line 117) | Codex hook limitation upstream |

### What Codex Has That Claude Code Doesn't (Leveraged by Sage)

| Feature | Codex Advantage | Sage Usage |
|---------|-----------------|-----------|
| **Git worktrees native** | Built-in worktree UI + Local/Worktree handoff | Sage relies on Codex native flows (README line 126–132) |
| **Native automations** | Standalone + thread automations (no Sage runner needed) | Documented template patterns; teams wire directly |
| **AGENTS.md session scope** | Loaded once per session (root → cwd walk) | Stronger always-on enforcement; constitution stays salient every turn |
| **UserPromptSubmit gate** | Pre-turn hook that can block + redirect | Unique enforcement lever; pre-prompt.sh uses it to gate build/fix/architect prompts missing .sage/work/ artifacts |

### Platform-Specific Behavioral Differences

- **Skill discovery:** Codex scans `.agents/skills/` up to repo root; Sage keeps that as primary surface (README line 72–73)
- **Workflow entry:** Claude Code uses custom `/sage:build` slash commands; Codex uses skill invocation `$build` (prompt-driven + skill UI)
- **Review:** Claude Code has `$review` (Sage workflow); Codex has native `/review` (diff viewer) + optional `$review` skill
- **Checkpoint approval:** Both use `[A] / [R]` notation; Codex can delegate to subagent only if Codex multi-agent execution available

Verifies end-to-end `sage init` → `sage update` cycle:

- **init --platform codex --preset base**

- **Merge fixture + regeneration**
  - Prepend user config to .codex/config.toml (model, features, native mcp_servers.native_keep)
  - Mutate `.agents/skills/api/SKILL.md`
  - Run project-local `./sage/bin/sage update`
  - Assert user config survived + managed block refreshed + mutated skill file unchanged (direct copy from source)

- **Prefix toggle cycles**
  - `init --prefix` → assert `sage:build`, `sage:fix`, `sage-navigator` (unprefixed)
  - Remove `command_prefix` from `.sage/config.yaml` → `update` → assert old prefixed dirs removed, unprefixed restored
  - Toggle `command_prefix: false` → `true` → assert stale variants pruned

- **Edge cases**
  - Command name exclusions: `/review` stays unprefixed (native Codex)
  - sage-navigator always unprefixed (line 178)
  - Skill refs inside skills rewritten correctly (line 188: `$sage:fix` references in `sage:fix` SKILL.md)

## Summary

The Codex adapter is a **conservative, release-ready port** that maps Sage's process engine onto three platform-native surfaces:

1. **AGENTS.md** — always-on constitution, 8 mandatory rules + 3 workflow gates, observable compliance signals
2. **.agents/skills/** — Codex discovery surface for workflow + direct skills (14 core workflows, optional direct skills)
3. **.codex/config.toml** — managed-block preservation strategy; MCP TOML encoding; no regeneration of hooks.json

**Enforcement layers** (in priority order):
- **L1:** AGENTS.md constitution (loaded once per session)
- **L2:** Workflow skill PREAMBLE (first-turn framing when `$build`, `$fix` invoked)
- **L3:** Opt-in hooks (pre-prompt.sh pre-turn gate, session-start.sh sticky context) — user must enable + copy

**Coupling to core/:**
- Minimal; command-prefix + skill-deployment decisions live entirely in the generator
- No platform-specific logic in workflows, gates, or skills
- Shared `.sage/` contract across all adapters (decisions, work, docs, gates)

**Test coverage:**
- Full E2E regression suite (init, update, prefix toggle, config merge)
- Hook unit tests (pre-prompt classifier, active-state computation, verification validation)
- No CI integration (deferred)

**Known limits (per current adapter docs):**
- Pre-prompt.sh gate is language-agnostic regex-based, empirically breaks on non-English/typos/synonyms (a6f1391 dead-end)
- ~~No file-edit PreToolUse gating (only Bash)~~ — **incorrect; see parent base doc, section 4.5 / assumption #2**
- Windows hook support not available upstream
- Codex multi-agent execution + guardian_approval not yet wired (documented follow-up)
